<objective>
Make the core loop work: tap the card, watch the ring fill, complete it, and undo a mistaken tap — with counter writes that cannot race and a past that cannot be rewritten.

Purpose: this is the interaction the whole product exists for, and it is also where the two nastiest correctness traps live — the undo/increment race and the "can I edit yesterday" question. Both are settled here, at the SQL layer, so no later phase can reintroduce them.

Output: atomic increment and compare-and-set undo in the DAO, `increment`/`undo` on the repository, whole-card tap handling, a filling progress ring, the completed card treatment, the Done-section move, and the undo snackbar.
</objective>

  <behavior>
    - Incrementing an achievement with no progress row for today creates the row and leaves `count = 1`
    - Incrementing a target-1 achievement once sets `done = true` and reports `justCompleted = true`
    - Incrementing a target-3 achievement twice leaves `count = 2`, `done = false`, `justCompleted = false`; the third sets `done = true` and `justCompleted = true`
    - A fourth increment past a target of 3 leaves `done = true` and reports `justCompleted = false` — completion is announced once per period, not once per tap
    - Fifty concurrent increments launched together produce a final count of exactly 50
    - Undo with a token from the immediately preceding increment decrements the count by exactly 1 and recomputes `done`
    - Undo with a stale token — one taken before a further increment landed — changes nothing and returns false
    - Undo twice with the same token applies once; the second call returns false
    - Undo can never drive the count below 0
    - A progress row keyed to a previous day is never touched by increment or undo, even when the injected clock is moved backwards so that "today" is again a day that already has a row
  </behavior>
  <action>
Add to `ProgressDao`: `insertRowIfAbsent(achievementId, periodKey, epochDay)` as a suspend `@Query` using `INSERT OR IGNORE` against the unique `(achievementId, periodKey)` index; `incrementAtomic(achievementId, periodKey, target, epochDay): Int` as a suspend `@Query` performing `UPDATE progress SET count = count + 1, done = ((count + 1) >= :target), updatedAtEpochDay = :epochDay WHERE achievementId = :achievementId AND periodKey = :periodKey` and returning the number of affected rows; `undoIfUnchanged(achievementId, periodKey, expectedCount, target, epochDay): Int` performing `UPDATE progress SET count = count - 1, done = ((count - 1) >= :target), updatedAtEpochDay = :epochDay WHERE achievementId = :achievementId AND periodKey = :periodKey AND count = :expectedCount AND count > 0` and returning affected rows; and `countFor(achievementId, periodKey): Int?`.

The `count = :expectedCount` clause is the whole design. It makes undo a compare-and-set that reverses one specific increment rather than blindly decrementing: if another increment landed in between, zero rows match and the undo is a no-op. That, plus `count > 0`, removes every case PITFALLS 9 describes without needing a separate mutation-log table or a per-achievement mutex — the atomicity lives in SQLite, where it cannot be bypassed by a fast double tap. Do not add a Kotlin-side read-modify-write helper alongside these; its existence is the bug.

On the repository add `suspend fun increment(achievementId: Long): IncrementOutcome` annotated `@Transaction` (or delegating to a `@Transaction` DAO method) so row creation, the counter update and the read-back of the resulting row are one unit. It resolves `todayKey = periodEngine.current(PeriodType.DAILY)` itself and never accepts a period key from its caller — that signature choice is what makes TRACK-05 and TRACK-10 structural rather than a runtime check someone can forget. It reads the achievement's `counterTarget`, calls `insertRowIfAbsent` then `incrementAtomic`, reads back the row, and returns `IncrementOutcome(newCount, isDone, justCompleted = isDone &amp;&amp; previousCount &lt; target, undoToken = UndoToken(achievementId, todayKey, newCount))`.

Add `suspend fun undo(token: UndoToken): Boolean` which returns false immediately if `token.periodKey != periodEngine.current(PeriodType.DAILY)` — a token that survived past midnight is refused rather than applied to a new day — and otherwise returns whether `undoIfUnchanged` affected a row.

Note for D-28: because both writes bind only the current key and undo additionally revalidates it, moving the device clock backwards cannot reopen a closed day. The old day's row is simply not the row today's key selects, and there is no code path that names a different one. No tamper detection is written, and none should be (D-27).

`IncrementUndoTest` runs under Robolectric against an in-memory database with an injectable `AppClock`, covering every case in the behavior list. The fifty-concurrent-increments case must launch its coroutines together on a multi-threaded dispatcher and await them all before asserting — a sequential loop does not exercise the race this test exists to catch.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI intent → counter write | The only mutating path in the app. Every write resolves its own period key internally; nothing external can name the period being written. |
| Device clock → period identity | The device clock is trusted outright per D-27. The boundary matters because it decides which row a write lands on. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-14 | Tampering | Rewriting a closed day by moving the device clock backwards | mitigate | Writes bind only `periodEngine.current(PeriodType.DAILY)`, and `undo` re-validates its token's key against today before applying. A past day's row is unreachable because no API accepts a period key. Covered by the named clock-rollback test (TRACK-10, D-28). |
| T-01-15 | Tampering | Counter corruption via interleaved increment/undo writes | mitigate | Single-statement atomic SQL for increment; compare-and-set `WHERE count = :expectedCount AND count > 0` for undo; both inside a transaction. Proven by the 50-parallel-increment and stale-token tests (PITFALLS 9). |
| T-01-16 | Repudiation | An undo token replayed after the app was backgrounded across midnight | mitigate | `undo` returns false when the token's period key is not today's. The stale snackbar action becomes a no-op instead of silently decrementing a fresh day. |
| T-01-17 | Denial of service | Increment held open across a long transaction, blocking the UI | accept | Writes touch at most two rows on a local SQLite file for a single user. `viewModelScope` keeps the call off the main thread via Room's suspend support. No further mitigation warranted. |
| T-01-18 | Information disclosure | Snackbar content on screen | accept | The snackbar carries only the word "Undo". No achievement content is surfaced. |
| T-01-SC | Tampering | Build-time dependency resolution | mitigate | No new dependencies. No npm/pip/cargo install exists in this project. |
</threat_model>

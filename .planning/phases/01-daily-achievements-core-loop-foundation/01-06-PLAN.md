<objective>
Give the streak a place to be inspected, and make the app notice when the day changes underneath it.

Purpose: two things the phase cannot ship without. TRACK-08 needs a surface for best streak, and D-13 wants that surface built now, read-only, so Phase 3's edit screen slots into an existing home. Separately, "a missed day resets the streak" is not actually true for a daily achievement unless the app notices midnight passing while it is open, and unless it survives a timezone change or a manual clock edit.

Output: a read-only detail screen reached by long-press, an observable current-period key that every read flow hangs off, and a watcher that refreshes and reconciles on date, time and timezone changes and on process resume.
</objective>

Add `androidx.lifecycle:lifecycle-process` to the version catalog against the existing `lifecycle` version ref (2.10.0) and to the app dependencies. This is the only build-file change in this plan; no other version moves.

`CurrentPeriodProvider(periodEngine: PeriodEngine)` holds a `MutableStateFlow<PeriodKey>` seeded with `periodEngine.current(PeriodType.DAILY)` and exposes it as `currentDailyKey: StateFlow<PeriodKey>` plus `fun refresh()`, which recomputes the key and assigns it — `MutableStateFlow` already suppresses equal values, so an unchanged day causes no downstream churn. This is the single source of "what day is it" for the whole app; nothing else may call `periodEngine.current` for a read path.

Rework `AchievementRepository.observeDaily()` to `currentPeriodProvider.currentDailyKey.flatMapLatest { key -> combine(achievementDao.observeActive("DAILY"), progressDao.observeForPeriod(key.value)) { … } }`, and do the same for `observeDetail`. This is what makes PERIOD-04 real: a key change re-subscribes the progress query against the new day, so an app left open across midnight shows yesterday's completed cards as not-done for today without the owner navigating anywhere. The write paths in plan 01-04 keep resolving today's key themselves and are unaffected.

`PeriodWatcher(context, currentPeriodProvider, reconcileStreaks, applicationScope)` exposes `start()` and `stop()`. `start()` registers a `BroadcastReceiver` for an `IntentFilter` carrying `Intent.ACTION_DATE_CHANGED`, `Intent.ACTION_TIME_CHANGED` and `Intent.ACTION_TIMEZONE_CHANGED`, registered via `ContextCompat.registerReceiver(..., ContextCompat.RECEIVER_NOT_EXPORTED)` — these are protected system broadcasts and API 34+ requires the export flag to be explicit. It also registers a `DefaultLifecycleObserver` on `ProcessLifecycleOwner.get().lifecycle`. On any of those signals — broadcast or `onStart` — it calls `currentPeriodProvider.refresh()` and launches `reconcileStreaks.runAll()` on `applicationScope`. The receiver is registered while the process is started and unregistered on stop, so nothing is left listening in the background. `AchievementFactoryApp.onCreate` constructs and starts it through `AppContainer`.

Three signals, one mechanism, covering all three cases PITFALLS 5 names: midnight passing with the app open, the owner editing the device clock, and travel across a timezone. Per D-27 a forward jump is simply a new day — the previous day closes with whatever it had and today starts fresh. Write no monotonic-clock cross-check, no elapsed-realtime comparison and no "suspicious jump" heuristic; travelling east genuinely does start a new local day and that is the wanted behaviour.

`CurrentPeriodProviderTest` asserts that `refresh()` with an unchanged injected date emits nothing new, and that advancing the injected date emits exactly one new key. `RolloverTest` runs under Robolectric: collect `observeDaily()`, complete an achievement so its card is done, advance the injected `AppClock` by one day, call `refresh()`, and assert the already-collected flow re-emits with that achievement at `count = 0` and `isDone = false` while the previous day's progress row is untouched in the database. Add a DST case that advances the injected date across a spring-forward boundary and asserts exactly one key change, not zero and not two.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| System broadcasts → app | `ACTION_DATE_CHANGED`, `ACTION_TIME_CHANGED` and `ACTION_TIMEZONE_CHANGED` are protected system broadcasts — only the OS can send them. The receiver is registered at runtime with `RECEIVER_NOT_EXPORTED` and declares nothing in the manifest. |
| Navigation argument → ViewModel | `achievementId` arrives as a typed `Long` route argument from within the app's own back stack. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-23 | Spoofing | A third-party app faking a date-change broadcast to force a rollover | mitigate | The three actions are protected system broadcasts that only the OS can send, and the receiver is registered with `RECEIVER_NOT_EXPORTED` and never declared in the manifest. Even a delivered signal only triggers an idempotent recompute from the real clock, so a spurious one is a no-op. |
| T-01-24 | Tampering | Detail screen accepting an out-of-range or hostile `achievementId` | mitigate | The argument is typed `NavType.LongType`, reachable only from this app's own back stack, and an unknown id resolves to the `NotFound` state rather than a crash or a wrong row. |
| T-01-25 | Elevation of privilege | Leaked broadcast receiver outliving the process foreground | mitigate | `PeriodWatcher.stop()` unregisters on the process lifecycle's stop; nothing stays registered in the background and no manifest-declared receiver exists to be started cold. |
| T-01-26 | Tampering | Clock manipulation to gain a streak credit | accept | Accepted per D-27 — see T-01-19. D-28's immutability caps the exploit at one credit per genuinely-elapsed local day, and the only affected party is the owner. |
| T-01-SC | Tampering | Build-time dependency resolution | mitigate | One dependency added: `androidx.lifecycle:lifecycle-process`, a first-party AndroidX artifact pinned to the `lifecycle` version ref already in the catalog. No version floats and no npm/pip/cargo install exists in this project. |
</threat_model>

Create the `com.achievementfactory.period` package. It must depend on nothing — no `android.*` import, no Room import, no Compose import. That isolation is the point: it is the only reason the whole correctness surface can be exercised by fast JVM tests.

`PeriodType` is an enum with `DAILY`, `WEEKLY`, `MONTHLY`. All three exist and are fully implemented and tested in this phase even though only `DAILY` is reachable from the UI — Phase 2 turns on the other two without touching this package, and the stored key format must be settled before any row is written.

`PeriodKey` is a `@JvmInline value class PeriodKey(val value: String)` wrapping the normalized key string. Formats: `DAILY` → the ISO date, e.g. `2026-08-12`; `WEEKLY` → the ISO date of that week's Monday, e.g. `2026-08-10`; `MONTHLY` → `yyyy-MM`, e.g. `2026-08`. All three are zero-padded and sort lexicographically in chronological order, which is what lets SQL order and compare them with no date parsing in SQLite.

`AppClock` is an interface exposing `today(): LocalDate`, `zone(): ZoneId` and `epochDay(): Long`, with a `SystemAppClock` implementation that resolves `Instant.now().atZone(ZoneId.systemDefault()).toLocalDate()` — converting from instant to civil date exactly once, at the boundary. Every consumer takes `AppClock` by constructor so tests inject a fixed date instead of reading the wall clock. Per D-27 the device clock is trusted outright: there is no monotonic cross-check, no tamper detection, and no suspicious-jump heuristic anywhere in this package.

`PeriodEngine(private val clock: AppClock)` exposes `keyFor(type: PeriodType, date: LocalDate): PeriodKey`, `current(type: PeriodType): PeriodKey`, `previous(type: PeriodType, key: PeriodKey): PeriodKey`, `next(type: PeriodType, key: PeriodKey): PeriodKey` and `startDateOf(type: PeriodType, key: PeriodKey): LocalDate`. Week start is computed with `date.with(TemporalAdjusters.previousOrSame(DayOfWeek.MONDAY))` — `DayOfWeek.MONDAY` written literally in the source. Month keys go through `YearMonth`. `previous` and `next` must parse the key back to its `LocalDate`/`YearMonth`, step with `minusDays(1)`/`minusWeeks(1)`/`minusMonths(1)` (or the plus equivalents) and re-derive the key string — never decrement the key text itself.

Banned in this package, and the acceptance criteria grep for them: `System.currentTimeMillis`, `Instant` arithmetic for boundaries, `+ 86_400_000`, `TimeUnit.DAYS`, `WeekFields`, `Locale.getDefault`, `Calendar`, `weekOfYear`, `weekOfWeekBasedYear`.

`PeriodEngineTest` is a plain JUnit4 test with no Android dependency, driven by a fixed `AppClock` fake. It must include, as separately named test methods: a DST spring-forward day and a DST fall-back day in a zone that observes DST, asserting the daily key advances by exactly one calendar day across each; a run across `2026-12-28` through `2027-01-04` asserting week keys advance by exactly seven days and never repeat or skip at the year boundary (2026 is a 53-week ISO year — this is the case ISO week numbers get wrong); month keys across a 28-, 30- and 31-day month and across a February in a leap year; `previous`/`next` round-tripping for all three period types; and a locale-independence test that sets `Locale.setDefault` to `Locale.US` and then `Locale.UK` around the same assertions, proving the Monday rule survives a device region change.

## Trust Boundaries

This is a single-user, device-local, zero-network Android app with no accounts, no IPC surface and no exported components beyond the launcher activity. The realistic threat surface is narrow and the register below reflects that rather than importing web-application threats that do not apply.

| Boundary | Description |
|----------|-------------|
| OS ↔ app process | The only inbound boundary. The launcher activity is reachable from the system launcher; nothing else is exported. |
| App ↔ device storage | The Room database file in the app's private data directory. Reachable only by this app's UID, or by anyone with physical access to an unlocked device or a rooted device. |
| Build host ↔ dependency repositories | Gradle resolves plugins and libraries from Google Maven and Maven Central at build time. |

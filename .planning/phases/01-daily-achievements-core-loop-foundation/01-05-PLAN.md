<objective>
Make the streak real: derived from the completion log, correct after any length of absence, ticking up the moment today is completed, and shown as a flame that only exists once there is something to protect.

Purpose: the streak is what the owner is actually protecting, so it has to be right in the case that is hardest to test — the app not being opened for weeks. Deriving it from the log with a bounded backward walk makes that case self-healing instead of dependent on bookkeeping that nothing was running to maintain.

Output: a pure `StreakCalculator`, a reconciliation pass that runs at app open and after every completion change, the cached streak columns kept honest, and the flame badge on the card.
</objective>

  <action>
`StreakSnapshot(current: Int, best: Int)` is a plain data class in `domain/streak/`.

`StreakCalculator(periodEngine: PeriodEngine)` exposes `calculate(doneKeys: Set<String>, currentKey: PeriodKey, periodType: PeriodType, storedBest: Int): StreakSnapshot`. It walks backwards: start at `currentKey` if it is in `doneKeys`, otherwise at `periodEngine.previous(periodType, currentKey)`; then step with `periodEngine.previous(...)` while each key is present in `doneKeys`, counting as it goes and stopping at the first absent key. `best = maxOf(storedBest, current)`. It must be pure — no Android import, no Room import, no clock read — so it is exercised entirely by fast JVM tests with fabricated logs.

Counting today when today is done is deliberate and is what makes the core loop work: completing an achievement has to make the number the owner is protecting go up in the same moment as the tap. An open, incomplete day neither counts nor breaks, which is why an achievement not yet done today still shows yesterday's streak.

`ReconcileStreaksUseCase(achievementDao, progressDao, periodEngine, streakCalculator)` exposes `suspend fun runFor(achievementId: Long)` and `suspend fun runAll()`. For each achievement it compares `streakCachedForPeriodKey` to `periodEngine.current(PeriodType.DAILY)`; when they match it returns without writing, and otherwise it loads `progressDao.doneKeysFor(id)`, runs the calculator and writes back through `achievementDao.updateStreakCache`. The whole pass must be idempotent — running it twice changes nothing the second time — because it runs on every app open and, from plan 01-06, on every resume and clock change. Add `AchievementDao.observeStale(currentKey)` or an equivalent suspend query so `runAll` can select only the achievements whose cache is behind, rather than rewriting every row on every launch.

The walk is bounded by the actual streak length — roughly 1,800 rows for a five-year daily streak, read once as an ordered key list — so there is no incremental "catch up from where we left off" state to get wrong. That is the entire reason this design survives the app being closed for a month, which is PERIOD-05.

`AppContainer` gains an `applicationScope` built as `CoroutineScope(SupervisorJob() + Dispatchers.Default)`, plus lazily-built `streakCalculator` and `reconcileStreaks`. `AchievementFactoryApp.onCreate` launches `container.reconcileStreaks.runAll()` on that scope. Plan 01-06 adds the resume and clock-change triggers for the same pass; do not add a `WorkManager` job or any background scheduler — reconciliation on open is the whole mechanism, by product decision.

`AchievementRepository.increment` and `.undo` call `reconcileStreaks.runFor(achievementId)` after their counter write so the streak the UI reads is already correct when the Flow re-emits. `observeDaily` must keep reading `currentStreak`/`bestStreak` from the cached columns and must not itself trigger a write — a read Flow that writes on collection re-triggers itself.

Returning after missed days produces no UI event of any kind: the number is 0, the flame is gone, and nothing announces it (D-26). No streak-reset history is recorded or surfaced (D-29) — the completion log exists because the calculator needs it, not as groundwork for v2 stats.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Completion log → streak cache | The cached streak columns are derived data. The boundary that matters is that nothing writes them except the reconciliation pass, so they can never drift from the log in a way the next pass will not repair. |
| Device clock → "which period is current" | Trusted outright (D-27). It decides where the backward walk starts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-19 | Tampering | Streak inflated by moving the device clock forward and back to fake completions | accept | Explicitly accepted per D-27 and PITFALLS 6. The only party who can do this is the owner, and the only thing defeated is their own motivation system. No monotonic-clock cross-check is built. D-28's immutability still prevents a *closed* day from being re-credited, so the ceiling on this is one completion per genuinely-elapsed local day. |
| T-01-20 | Tampering | Streak cache drifting from the completion log | mitigate | The cache is never incrementally mutated; it is only ever overwritten by a full re-derivation from the log. Any drift self-repairs on the next reconciliation. Proven by the idempotence test. |
| T-01-21 | Denial of service | Unbounded backward walk on a very long history | mitigate | The walk is bounded by the streak length and reads an ordered key list once. A five-year daily streak is roughly 1,800 keys. Reconciliation runs off the main thread on `applicationScope`. |
| T-01-22 | Information disclosure | Streak history exposed in UI | mitigate | No history surface exists (D-29). Only the current and best numbers are rendered. Grep-gated. |
| T-01-SC | Tampering | Build-time dependency resolution | mitigate | No new dependencies. No npm/pip/cargo install exists in this project. |

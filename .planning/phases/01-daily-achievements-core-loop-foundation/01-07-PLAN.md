<objective>
Build the moment the whole app exists for: the completion celebration — fired exactly once, sequenced as one gesture, and honouring reduced motion from day one.

Purpose: this is the core value. It is also the single most common architectural trap in this app shape, because a celebration derived from persisted state re-fires on every rotation and every scroll, turning the best moment in the product into the most annoying one within a day. The event plumbing built here is what Phase 2's tier variants and Phase 5's full-tab burst hang off, so it has to be right before anything animates.

Output: a non-replaying celebration event stream, the sequenced ring-close → checkmark-morph → flame-tick → card-sink treatment, a single `MotionSpecs` source for every timing value, and the reduced-motion collapse every later celebration inherits.
</objective>

  <action>
`CelebrationEvent` is a sealed interface in `ui/celebration/` with a single `Completed(achievementId: Long, newStreak: Int, isFirstFlame: Boolean)` case in this phase. Phase 2 adds tier variants alongside it, which is why it is sealed rather than a data class. `CelebrationStage` is an enum with `RING_CLOSED`, `CHECK_MORPHED`, `FLAME_TICKED` and `SETTLED`.

`DailyViewModel` gains `private val _celebrations = Channel<CelebrationEvent>(Channel.BUFFERED)` exposed as `val celebrations: Flow<CelebrationEvent> = _celebrations.receiveAsFlow()`. `onIncrement` emits into it only when `IncrementOutcome.justCompleted` is true — that is, only at the transition edge, computed by the repository at the write, never inferred by a composable from a state snapshot. `isFirstFlame` is `newStreak == 1`.

The event type must never be persisted, never be added to `DailyUiState`, and never be derived from `isDone`. That is the entire mechanism behind CELEB-04, and it is the reason a `Channel` with no replay is used rather than a `StateFlow`: a new collector after rotation or process recreation receives nothing until the next real emission. The known cost — an event can be dropped if the process is backgrounded at the exact moment of the tap — is deliberately accepted, per ARCHITECTURE.md: a missed animation is a far cheaper failure than a spurious one.

`DailyViewModel` also gains `onCelebrationSettled(achievementId: Long)`. On emitting an event it adds the id to the `heldBackIds` set that plan 01-04 wired into `DailyUiState.Content`; on `onCelebrationSettled` it removes it. That set is what keeps a just-completed card in the outstanding group while its celebration plays, so the sink reads as a consequence of the celebration rather than something that interrupts it (D-06).

`DailyScreen` collects `celebrations` inside `LaunchedEffect` + `repeatOnLifecycle(Lifecycle.State.STARTED)`, exactly as it already collects `undoRequests`, and records the celebrating achievement in local composable state that Task 2's animation consumes.

`CelebrationEventTest` is a JVM Turbine test over a fake repository covering every case in the behavior list, including the late-collector case — collect once, receive the event, cancel, collect again, and assert no emission arrives.

`CelebrationInstrumentedTest` in `androidTest` covers the two cases only a device can prove: complete an achievement then recreate the activity and assert no second celebration is triggered; and complete an achievement, background and restore the app, and assert the same. Write it now even though it needs a device to run — it is compiled by `assembleDebugAndroidTest` in every automated gate and is executed in the end-of-phase device pass.

`MotionSpecs` is an object in `ui/theme/` holding every timing value in the phase, so no duration is ever written inline in a composable: `ringSweep` = `tween(150, easing = FastOutSlowInEasing)`; `ringClose` and `checkMorph` and `flameTick` = `spring(dampingRatio = Spring.DampingRatioMediumBouncy, stiffness = Spring.StiffnessMedium)`; `flameUnlock` = `spring(dampingRatio = Spring.DampingRatioLowBouncy, stiffness = Spring.StiffnessLow)`; `cardSink` = `spring(dampingRatio = Spring.DampingRatioLowBouncy, stiffness = Spring.StiffnessLow)`; `CHECK_MORPH_DELAY_MS` = 250; `FLAME_DELAY_MS` = 400; `reducedCollapse` = `tween(90, easing = LinearEasing)`.

Alongside them, `rememberReducedMotion(): Boolean` reads `Settings.Global.getFloat(contentResolver, Settings.Global.ANIMATOR_DURATION_SCALE, 1f)` and treats `0f` as reduced-motion-on, per UI-SPEC. Expose a single accessor that resolves any spec through it — when reduced motion is on, every spec above resolves to `reducedCollapse` and every stage delay resolves to 0. This one accessor is the shared code path UI-SPEC requires Phase 2's tier variants and Phase 5's full-tab burst to reuse rather than reimplement, so nothing outside `MotionSpecs` may read the animator duration scale directly.

`CompletionCelebration(event: CelebrationEvent.Completed?, accent: Color, onStage: (CelebrationStage) -> Unit, onCelebrationEvent: (CelebrationStage) -> Unit = {})` drives the four stages off a single `Animatable` progress value, so the escalation logic lives in one place rather than scattered per-composable. Stage timing follows UI-SPEC exactly: the ring closes from t=0 with `ringClose`; the glyph morphs into a checkmark with a 1.0 → 1.15 → 1.0 scale pulse starting at `CHECK_MORPH_DELAY_MS`, only once the ring is visibly near-closed; the flame badge scale-pulses from `FLAME_DELAY_MS`. When `event.isFirstFlame` is true the badge instead plays the unlock treatment — `flameUnlock`, scaling 0 → 1.3 → 1.0 with a brief flash of the achievement's own accent — visibly bouncier than every subsequent tick, because the flame's first appearance should read as a small unlock rather than another state change (D-08, D-22). After the last stage it emits `CelebrationStage.SETTLED`, which `DailyScreen` forwards to `onCelebrationSettled`, releasing the card to sink with `cardSink` over roughly 400–500ms (D-06). The sink is gated on that callback, never on a fixed `delay`.

`onCelebrationEvent` is the Phase 5 attachment point (D-24): it is invoked with each `CelebrationStage` and defaults to a no-op. No haptic call, no `Vibrator`, no `VibratorManager` and no `performHapticFeedback` may appear anywhere in this phase — CELEB-05 is wholly Phase 5, and the hook exists so that phase is an addition rather than a rework.

The checkmark is a `Path`-driven shape animated out of the closing ring on the same `Canvas`, not an icon swap — it has to grow continuously out of the ring for the moment to read as one connected gesture (D-11, UI-SPEC Design System). `ProgressRing` and `StreakFlameBadge` take animated values as parameters; neither owns an animation clock of its own, so the sequencing stays in `CompletionCelebration`.

The celebration must not block input: a tap on another card during the animation is accepted immediately, and the animation is interruptible. A daily-driver app that makes its owner wait through an animation teaches them to dread it.

No confetti and no particle system (D-23). Konfetti stays out of the dependency graph until Phase 5's full-tab moment, so the escalation from a small tick to a full-tab burst still means something when it lands.
